# 申請制度

# Problem

每個新成員的申請都需要處理，自介需要能被保留與讀取；提出申請、審查通過及成為成員也需要分清楚。詳見[加入申請的處理成本](../02-工作流/[機制]志工協作與開源知識.md#我們能不能減少我們的營運成本)。

# Specs

## 申請與成員資格

加入本組織的唯一的門檻是以 PR 提交自介。自介審查通過後，提交者即加入本組織，成為成員。

提交自介 PR 表示提出申請，不等於審查已通過。GitHub Organization Member、Discord 身分與本組織成員資格不自行視為同一件事；Discord 邀請不是入會門檻。

## 自介內容與提交位置

自我介紹放在公開 GitHub Repo 的 Members 資料夾。自介寫出自己是誰、想 share 的東西，以及自己的 R&R：可以幫什麼忙、想要幫什麼忙。

自介內容提供協作資訊，不代表申請者或成員已承諾接受任何指定工作。

## 自介審查

審查依[憲法第 11 條（成員加入原則）](./constitution.md#第-11-條成員加入原則)及[第 17 條（開放參與原則）](./constitution.md#第-17-條開放原則)。

自介的審查看內容有沒有真誠，不看文章品質。自介由 AI 寫，是很正常的。

自介很真誠，所以值得信任，但沒有經歷、沒有專案的人，可以加入。

自介的審查與開放心態並存：開放心態講的是背景，審查看的是有沒有真誠。基本參與度義務依[成員參與制度](./[機制]成員參與制度.md)。

## 制度修改

本制度依[憲法第 20 條（制度修改關係）](./constitution.md#第-20-條修憲建議與修改)在自己的 Plan 記錄變更並接受憲法檢查；調整申請方式或審查安排，不必因為這些具體安排而修憲。

## 審查安排的候選做法

審查的候選做法是由一小群核心成員共同承擔，避免集中在一個人身上；由誰審查、權限如何決定仍未定案。國會制度、投票、Council、Teams、核准數與自動邀請都是候選安排，尚未採納。

有平認領自介準則與 Onboarding 篩選的工作，不等於已被定為唯一審查人。Landing Page 對外之後，如果更多人提出申請，如何依既有真誠與意圖原則完成審查，仍需要設計。
