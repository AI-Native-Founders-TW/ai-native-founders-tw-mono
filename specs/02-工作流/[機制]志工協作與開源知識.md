# Problem

## 每個人也都在上班，每個人也都有自己的事情

組織需要持續的貢獻，但成員是志工，各自也有工作與生活。成員可以用自己的方式貢獻；若先替每個人貼上攝影、活動等標籤，再要求他照分派工作，可能卡在官僚機制而做不下去。

1. 成員能投入的時間有限，也有自己在乎的事情；組織需要分工，卻不能把分工變成每個人都必須幫忙。
2. 一件事情可以由多人一起做，仍需要有人拍板；共同協作與有人負責決定要同時成立。
3. 成員關心自己做的事情能留下 credit；投入的工作需要能被看見，讓人知道有哪些人參與貢獻。

## 我們能不能減少我們的營運成本

每個新成員的申請都需要處理，自我介紹也需要一個能被保留與讀取的位置。使用 LINE 記事本存放自介時，需要考慮空間使用與費用；改變存放方式之外，也需要降低逐一處理申請的成本。

1. 加入方式要讓人表達學習及貢獻意圖，但組織不看背景、實力和經歷。不能為了方便審查，改以寫作能力或專案數量判定資格。
2. 自介可能由 AI 協助撰寫，因此是否由 AI 寫，不能取代對內容真誠與意圖的判斷。
3. 人變多以後，不可能每個人都先互相熟識。如何在不認識本人的情況下建立信任，仍需要設計；目前沒有採用必須視訊、見過本人等額外資格。

## 找人幫忙時，得一個一個去問

成員可以幫什麼忙、想幫什麼忙，若只散在每個人身上，發起事情的人就得一個一個去問。向 AI 詢問誰可能願意幫忙時，也需要先讓 AI 取得這些 context。

1. 找人需要知道成員自己表達的能力與意願；知道某人有能力，不代表對方已答應幫忙。
2. 規格、計畫、自介與貢獻需要能一起查找；如果各自存在不相連的位置，就難以理解目前在做什麼、可以找誰。
3. 衍生的程式碼又可能由不同人各自維護；共同入口與各自開發的安排需要同時保留。

## 社群媒介與主動參與

LINE 群有 500 人限制，也面臨詐騙與被動潛水的問題；但不是每個人都在用 Discord。換一個媒介，需要面對既有使用習慣，不能把換平台本身當成大家會主動參與的保證。

1. 社群希望有主動的 engage，而不只是加入大群之後潛水；但基本參與度與強制幫忙仍是不同的事。
2. 熱絡是個假議題：重要的是大家記得為什麼加入，當有人發起有意義的事情時願意參與，而非平常一定要一直說話。
3. 需要讓成員知道在哪裡交流，但交流媒介不應被誤讀成另加的入會資格。

## 會不會有可能也是會變成資訊量太多

組織用開源筆記記錄故事與創業流派，內容累積之後，新人卻可能不知道從哪裡開始。例如，YC Startup School 多年累積的影片，即使想看，也可能因為不知道怎麼開始而留待下次。

1. 知識要保留深度與適用情境，也要讓新人找到與自己有關的內容；持續累積與容易取用需要一起考慮。
2. AI 會配合提問者的認知；當創業者還不知道該怎麼思考，只問「我該怎麼創業」，回答仍難以達到他需要的深度。除了找到資料，也需要讓創業者能更深入地理解自己的情境。

# Specs

## 範圍與整體運作

本檔整理已確認的志工協作方式：用 Discord 交流，依申請制度處理加入，透過 Mono 連接規格、計畫、自介與貢獻，再由成員認領在乎的事情。成員資格依[申請制度](../01-制度/[機制]申請制度.md)，基本參與度依[成員參與制度](../01-制度/[機制]成員參與制度.md)，拍板規則以憲法為準。

這份文件說明已確認的安排，不表示 Discord 搬移、Members 資料夾、GitHub 權限或 submodule 已完成設定；設定與執行的進度由各自 Plan 記錄。

| 對象 | 在協作中的作用 |
|---|---|
| 申請加入的人 | 依申請制度提供申請資訊 |
| 成員 | 依申請制度加入、依成員參與制度參與，可用自己的方式貢獻 |
| Owner | 依憲法認領自己最在乎的事項；其他成員也能一起做 |
| Discord | 社群交流與邀請的媒介，不是加入資格 |
| Mono Repo | 規格、計畫、自介與貢獻的共同入口 |
| 獨立 Repo | 維護衍生程式碼，透過 submodule 掛進 Mono |

## 加入與自介

申請方式、自介內容與提交位置、審查及成員身分取得，依[申請制度](../01-制度/[機制]申請制度.md)。本工作流接續制度中的申請與協作資訊，不另定一套申請規則。

## 社群搬到 Discord

社群從 LINE 搬到 Discord，LINE 群不再使用，之後邀請一律使用 Discord。Discord 會邀請加入，但不是入會門檻；加入身分仍依[申請制度](../01-制度/[機制]申請制度.md)。

這個選擇是為了離開原有 LINE 群的限制並支持主動交流；它沒有新增每週發言、開會次數或活動出席的要求。基本參與度的具體標準仍待決定，依[成員參與制度](../01-制度/[機制]成員參與制度.md)。

## Mono 與衍生的程式碼

一個 Mono Repo 放規格、計畫、所有人的自介與貢獻。衍生的程式碼另開獨立 Repo，以 submodule 掛進 Mono，讓大家可以從共同入口找到各自維護的內容。

自介所保存的能力與意願，也作為向 AI 詢問「有誰會願意幫這個忙」的 context。AI 找到相關人選，不代表已取得對方同意，也不會代替成員認領事項。

每個人做的事情應留下 credit；開源筆記如何附上資訊貢獻者，依[憲法第 10 條（資訊貢獻留名）](../01-制度/constitution.md#第-10-條資訊貢獻者署名)。其他貢獻的具體呈現與激勵方式仍待設計。

## 認領與拍板

成員依[憲法第四章（協作與分工）](../01-制度/constitution.md#第四章協作與分工)認領自己最 care 的事項，並與其他願意幫忙的成員共同進行。Owner、參與工作的人與拍板的要求，依該章判定。

## 開源知識如何被使用

筆記承接[願景中的知識整理與持續維護](../00-願景和問題/vision.md#我們希望留下什麼)。新人如何從持續增加的知識找到適合自己的內容，尚沒有選定完整方案；現有的整理與維護承諾仍成立，Skill 與文件 MCP 則保留在下方 Note，不能當成已完成的能力。

## 實例：想幫忙，不等於已被分派

假設一位成員在自介寫自己能協助某件事，也想分享相關經驗。另一位成員從 Mono 的 context 找到他，並不表示對方已接受工作；後續仍由成員依自己的意願參與或認領。事情有人認領之後，其他人仍可以幫忙，並依憲法保留至少一人拍板的要求。

審查人與 repo 權限尚未決定；每個事項由誰拍板，也需要在該事項中確定。

# Note

## Skill 與文件 MCP

候選做法是讓新人使用 Skill，由 Skill 跟他聊天、訪談，將他內在有價值的地方引出來；或提供文件庫，讓 AI 找相關內容。下一代 AI 的知識與思考，可能比額外的 Skill 更好；深入整理仍有價值，但 Skill、MCP、訪談流程與交付方式尚未選定。

## 誰審與篩選意圖

誰審、篩選意圖及權限的未決事項與候選安排，見[申請制度](../01-制度/[機制]申請制度.md#審查安排的候選做法)。

## 基本參與、線下與分組

基本參與的已確認規定、未決標準與線下活動候選安排，見[成員參與制度](../01-制度/[機制]成員參與制度.md)。

是否限縮賽道，以及如何在廣泛參與與更深的 connection 之間安排分組，仍見[願景的範疇與資訊揭露](../00-願景和問題/vision.md#範疇與資訊揭露)。

## 激勵與大量 PR

GitHub Star 能表達部分支持，但是否符合組織需要的激勵，仍未決定。每個 Repo 掛進 Mono 後各自可以被按 Star，也還不能解決整個激勵問題。

當同時出現很多 PR，例如八十幾個 PR 時，持續整合與審查如何處理，尚沒有完整設計。不能以已決定使用 PR，就推定大量協作的問題已解決。
