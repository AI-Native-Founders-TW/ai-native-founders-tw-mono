# 提出提議或活動與號召討論

有想法想聽大家意見、想改善一件事，或想找人一起辦活動時，可以先在 mono 的 GitHub Issues 發起討論。不必先有完整解法、找到所有協作者或寫好 Plan。

## 怎麼做

1. **先看看有沒有相同討論。** 在 mono 的 Issues 搜尋相關主題；已有相同事項就接續留言，避免大家分散討論。
2. **開一個 Issue 說明想法。** 標題直接寫想做什麼，內文先說清楚下面三件事即可；不知道的可以寫「還沒想好」。活動的時間、地點或形式若有想法也可附上，尚未確認就標明暫定。
   - 我想提議或舉辦什麼？
   - 為什麼想做，或目前遇到什麼問題？
   - 希望大家提供哪些意見，或一起幫什麼忙？
3. **到 Discord 號召。** 活動分享至 `events`，協作分享至 `collaborations`；附上 Issue 連結，簡單說明想討論什麼。可以在 Discord 交流，把影響下一步的重要結論與本人接受的工作補回 Issue，不要求逐句搬回聊天內容。
4. **有進展就更新下一步。** 按下表接續，不必每件事都建立 Plan，也不用為了讓 Issue 看起來完整而猜出答案。
5. **留下目前結果。** 在 Issue 說明已完成、持續討論、等待有人承接或暫不進行。完成或決定停止時寫明結果與理由，再由有權限者關閉；結束討論不等於活動或工作已完成。

## 討論後怎麼接續

| 目前情況 | 下一步 |
|---|---|
| 還不清楚問題或做法 | 繼續在 Issue 整理例子與待釐清事項，不急著寫完整方案。 |
| 改動簡單、在既定職責內 | 找對應 Leader 確認決定，由願意承接的人執行；修改文件時可直接接 PR 並連回 Issue。 |
| 需要協作者或活動執行者 | 列出需要的協助，由本人明確接受工作；沒有回覆就維持未承接，不自動指派。 |
| 需要整理規格變更、分工、相依與驗收 | 先看是否已有適合的 Plan，將 Issue 接到既有 Plan；確有獨立範圍才依 repo 規範另建，不因開了 Issue 就必須開 Plan。 |
| 涉及跨 R&R 決定、共同資源或對外合作 | 準備好要共同決定的內容，再走[共同事項與表決 SOP](<憲政/[SOP]提出共同事項與參與表決SOP.md>)。 |
| 涉及任命、罷免或制度修改 | 從[憲政 SOP 入口](<憲政/README.md>)選對應流程，不把一般留言當成正式表決。 |

活動號召與正式決定分開：討論想辦什麼不等於已核准使用組織資源，也不替尚未接受的志工承諾工作。一般活動與頻道使用依[Discord 社群 Setup](<../05-社群基建/[規格]Discord-社群-Setup.md>)；不是所有活動都要經共同表決。

活動確定要籌辦後，依[活動籌備、舉辦與會後整理](<[SOP]活動籌備、舉辦與會後整理.md>)接續公告、參與安排及會後紀錄。

## 開 Issue 不代表什麼

- 不代表提議已通過、活動確定舉辦，或任何人已接受工作。
- 不代表正式討論期或投票期開始。進正式程序時，要明確公布完整案件、適用規則與起訖時間並通知；先前聊天、回覆及表情反應不自動計為正式票。
- 不代表已取得組織成員或決策資格。公開討論與正式提案、投票的資格分開，不能以能留言推定有治理權。

## 沒人回覆或有其他狀況

沒有回覆時，可以補充具體例子、縮小希望大家協助的範圍，或在相關頻道再分享；沒有回覆不等於同意，也不必因此無限期等待。暫不進行時留下原因即可。

已有明確且簡單的修正，可直接 PR 或執行既定 SOP，不為形式補開 Issue。正在發生的入侵、資料刪除等傷害，依[緊急處置](<../01-制度/[機制] 憲政制度.md#緊急處置>)先處理，不等待討論；公開 Issue 不放密碼、憑證或私人資料。

制度依據：[工作承接](<../01-制度/[機制] 憲政制度.md#routine-與-non-routine-responsibilities>)、[決策範圍](<../01-制度/[機制] 憲政制度.md#council-與-rr>)、[正式案件與投票](<../01-制度/[機制] 憲政制度.md#提案紀錄與投票程序>)。
