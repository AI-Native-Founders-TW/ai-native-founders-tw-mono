# Problem

1. 自介 PR 的審查人需要依同一套標準判斷內容是否足夠，讓申請者知道哪些內容要補充，以及審查通過後如何完成 GitHub org 加入。
2. 若只留言「通過」或「不通過」，申請者無法知道理由與下一步。
3. 若把審查通過、PR 合併、邀請送出及接受邀請當成同一件事，資料與權限便可能與實際狀態不一致。

# Specs

## 適用範圍與執行前提

本 SOP 承接[申請制度](../01-制度/[機制]申請制度.md)、[自介審查](../01-制度/[機制]自介審查.md)及 [members 提交說明](../../members/README.md)，處理本 repo 的自介 PR。Council 人員正式裁決，AI 協助；一位合格審查人核准、不得自審、未解決異議不得通過的規定，統一依自介審查制度。審查人先核對自己的 Council 身分與本次 PR 作者；沒有符合資格的人時，維持待審。

操作開始前確認本次所需的審查、合併與 org 邀請權限，沒有權限的動作交給有權限的人接續。平台有按鈕不等於制度授權；制度允許操作也不表示平台已開通。

嚴格是逐項核對既有要求、指出具體依據與未完成處，不是提高背景、能力、經歷、寫作品質或作品數量門檻。使用 AI 寫自介本身不是不通過的理由。

## 審查標準

每項記錄「符合／待補充／有具體衝突」與檔案位置。資訊不足先指出需要釐清的內容，不憑語氣、文筆或照片推定不真誠。

| 檢查項目 | 符合的內容 | 待補充或需釐清的情況 | 依據 |
|---|---|---|---|
| 自介與帳號 | 自介位於 members，能辨識本人稱呼與 GitHub 帳號；PR 作者與受邀帳號能對應。 | 帳號缺漏、對不上，或無法確認提交對象。 | members 提交說明及 GitHub 邀請的對象核對。 |
| 照片 | 自介引用 members/assets 下本人願意公開的一張照片，能正常顯示。 | 沒有照片、引用失效，或本人尚未確認願意公開。 | 申請制度；不要求正式照、外貌條件或身份證件。 |
| 加入動機與期待 | 說明為什麼加入、想獲得什麼；探索中的想法也可如實說明。 | 仍留 placeholder，或缺少足以理解本人想法的內容。 | members 提交說明；不以文章品質評分。 |
| 分享與 Contributions | 寫清楚想分享什麼、可以幫什麼忙、想要幫什麼忙，符合本人意願。 | 尚未填寫、留待以後補，或內容存在需要本人釐清的矛盾。 | members 提交說明；不要求亮眼經歷或指定工作承諾。 |
| R&R assignment | 自行選擇至少一個 R&R 當 Contributors，可選多個；assignment 與 members 索引一致。 | 未選擇、兩表不一致、代替別人認領，或把待確認 Leader 寫成已就任。 | 成員參與制度。 |
| 本人 review 與公開資料 | 本人確認全文真實、符合自己的想法，沒有 AI 編造或不願公開的個資。 | 未確認、出現明確矛盾或疑似誤公開資訊，需要本人說明或修正。 | members 提交說明；不使用 AI 偵測器作為真誠判定。 |
| 參與意圖 | 表達正向學習與貢獻意圖，願意遵守現行制度。 | 明確表達與憲法或制度相衝突的意圖；審查須引用具體原文與條文。 | 憲法及申請制度；不能以背景或經歷替代判斷。 |
| PR 變更範圍 | 自介、照片與本人兩表資料相符；沒有夾帶不相關的設定或他人資料變更。 | 修改別人的 assignment、設定、程式或不相關資料。 | members 提交說明。 |

## 核對、comments 與接續

1. 開啟 PR，讀取最新變更、完整自介、圖片與兩表，不只看 PR 描述。記錄本次查看的 commit，並核對既有 comments，避免重複要求已補完的內容。
2. 依上表逐項核對；需要補充時，指出具體檔案、內容、依據及可完成的修改，不以「誠意不足」作為沒有證據的結論。
3. 依自介審查制度判定結果，將結果、檢查版本及具體依據寫入 PR。
   - 需要補充：發布下方「待補充 comment」，可用 Request changes 表達需修正內容，保持 PR 開啟；等待本人修改後重新核對，不排定定期催辦或逾期關閉。
   - 有未解決異議：維持待審，釐清並記錄結果；不能因有人 Approve 就繼續合併或邀請。
   - 明確違反原則：由 Council 審查人正式裁決，發布「正式未通過 comment」，再由有權限的人關閉 PR；不合併或發送 org 邀請。回讀確認已關閉，若無關閉權限則交接並如實記錄。
   - 全部符合且無未解決異議：由 Council 審查人提交 Approve 與「正式通過 comment」，記錄審查版本。申請者不是自己的審查人。
4. 正式通過後，由有合併權限的人核對最新內容、有效核准、未解決異議、衝突及平台要求。核對 members 總表、自介與 R&R assignment 的資料；將通過者由申請中移入成員表，連到正式審查結果，同步移除 assignment 的申請中標記。若因此新增 commit，重新核對受影響內容並確認核准適用於最終版本，再合併。平台阻擋、衝突或合併失敗時保留已通過結果，回報尚未合併的原因，不繞過檢查或宣稱已合併。
5. 回讀確認 PR 已合併，再由 org Owner 依 [GitHub org 加入規格](./[機制]GitHub-Org-Setup.md#審查通過後的-github-org-加入)執行：核對 username 與既有 Members／Invitations，選 **Member**，不勾選 Members、Council 或其他 Team，送出邀請並確認 pending invitation。已是 org Member 時不重送；既有 Team／權限不由此流程移除。邀請失敗時記錄實際原因與接手人，不把 PR 合併當作加入完成。
6. 送出邀請後發布下方「邀請已送出 comment」。本人回覆接受、詢問加入狀態或需要接續未完成案件時，再查看 GitHub People／Invitations 的實際狀態；確認已加入才發布「歡迎正式加入 GitHub org comment」。不因沒有回覆自動撤回已通過結果或另設定期催辦。
7. 邀請失效時，先重新核對帳號、通過紀錄與現有邀請；本人仍要加入且尚未是 org Member 時，由 org Owner 重送 Member 邀請。操作失敗或等待本人處理平台驗證時使用「邀請未完成 comment」，記明誰接續及需要完成什麼。平台接受條件不追加為組織能力或背景門檻。

每次接手先看既有 PR comments 與 GitHub 實際狀態；不重複留言、合併或發邀請。先前留言的狀態有變時，補一則具體進度或更新原有狀態說明，保留正式審查結果的依據。尚未完成的步驟及接手人留在該 PR，不另建立第二份成員資格來源。

僅在 Council 已正式裁決為明確違反組織原則時使用；補件中的申請不使用本段。

>
> 具體原因：`<自介中的具體內容及位置>` 與 `<現行規定連結及要求>` 不符。`<說明兩者如何衝突；不能只寫主觀評語。>`

> 本次 PR 將關閉。若你願意依上述規定修正，請開新的自介 PR，連回本次 PR 並說明修改位置；Council 會依重新提交的內容審查，不因前次未通過就直接拒絕。
