# R&R assignment

每個 R&R 的 Leader 與 Contributors 依[成員參與制度](<../specs/01-制度/[機制] 憲政制度.md#rr-assignment>)維護。每位成員至少自行選一個 R&R 當 Contributors，可選多個；Contributions 留在個人自介。

各 R&R 的責任、routine、non-routine 與 SOP 引用由 [R&R package](<../specs/02-R&R/README.md>) 維護；下表只維護人員 assignment，不另存責任範圍。

下表是 assignment 的唯一維護來源；成員以 Member ID 核對，顯示本人稱呼並連到個人自介，並同步到 [members 總表](members.md)。申請者標示「申請中」，不能因此視為已成為成員。待確認與尚無登錄都表示資料未完成，不是人名，也不表示該分工已有人負責。

初始 R&R 範圍取自[第一次核心會議記錄](../logs/20261024-第一次核心會議-會議記錄.md)。歷史認領與新 assignment 的差異及待確認人選保存在 [Kickoff 的初始認領核對](../plans/001-Kickoff/plan.md#初始認領核對)。目前尚無經本人確認的新 assignment；不將會議中的負責／協作直接轉成 Leader／Contributors。

各 R&R 文件中的尚未訂定事項不因有人加入 assignment 而成為已採納規則；實際安排依 specs。Leader 待確認的項目尚未完成決策分工。

## 填寫方式

1. 選擇自己要加入的 R&R，在 Contributors 欄加入連到自己自介的本人稱呼，連結旁附 Member ID；尚未配置時附「待配置」與 GitHub 帳號；同一個 R&R 有多人時全部保留。
2. 在 members 總表自己的那一列，列出所有已選 R&R，逐一連到本表對應列，標明 Leader 或 Contributors；兩種身分都有時兩者都列。
3. 變更 Leader 時附上有效任命／替換決定、生效時間及接任者本人接受紀錄，依憲政制度處理；不替其他人完成認領。
4. 同一個 PR 一起更新兩表。審查時核對每位成員有至少一個 Contributors assignment，且所有人名、自介與 R&R 的連結都對得上。

編號、帳號唯一性及變更規則依[成員識別與資料](<../specs/01-制度/[規格]成員識別與資料.md>)。顯示名稱可以重複；不可用名稱相同推定為同一人。帳號變更或編號配置時同步連結與識別資料，不因此變更 assignment。
