# 憲法正式潤稿與修憲建議釐清

## 需求原文

```text
拜託寫得專業一點好不好？什麼叫做「留下所有有留下經歷和見解的大大的名字」？什麼叫「大大」？這整個拜託你全部潤過一遍，好不好？

然後「提出憲法的建議」那裡寫得不夠清楚。

再來，我剛發現你加上了 HTML 的 link 標籤，不需要，這是 Markdown，把那些格式都拿掉，謝謝
```

## 使用者目前覺得的 Problem

### 憲法語氣口語，修憲建議不清楚，另有多餘 HTML

憲法將口語原話直接當作條文，出現不適合正式規範的稱呼與表達；修憲建議的記錄內容及其與現行條文的關係也不明確。使用者明確要求刪除 HTML，保留 Markdown。

## To-Be 目標

1. [憲法](../../specs/01-制度/constitution.md)全文採正式、直接且可理解的條文語氣，保留既有核心原則與制度分工。
2. [第二十條（修憲建議程序）](../../specs/01-制度/constitution.md#第-20-條修憲建議與修改)明定修憲 Plan 記錄的條項、原文、建議文字及理由，區分提出建議與已採納條文。
3. 純 Markdown 標題與 number list 保留條號、項號；所有 HTML 標籤移除，引用改用標題連結與文字條項定位。

## 工程摘要

本 Plan 專門修改憲法。依使用者本輪明確授權潤稿，不把口語逐字保存的規則誤套到正式條文；歷史需求原文、會議原話與創辦人的話仍不改寫。

### 主要修正

- 資訊貢獻者以姓名或署名記錄，不再使用口語敬稱；不要求實名、不刪除原有署名義務。
- 正式說明組織目的、非營利、開放、認領、決策及衝突處理，移除中英混雜與語意含糊的口語，未新增背景、工作或參與門檻。
- 修憲建議須於專門修憲 Plan 記錄擬修改條項、原文、建議文字與理由；未確認採納的建議不作為現行規則。交付與推送前仍須完成憲法檢查。
- 修憲提案權、核准者、提出管道及通過門檻，在既有規格、歷史 Plan 與會議紀錄中均未正式明定；本輪不將 Council、投票或任何人選補為既定制度。已向使用者提出缺少的核准人問題；沒有新答覆時先保留未決，不影響本輪語句潤稿。
- 憲法不使用 HTML；刪除條項及章節的手動錨點。條號及項號不變，標題連結隨正式名稱同步。歷史 Plan 的可點擊目的地修正，原文與當時檢查結果不改寫。

接手時願景、憲法另有人工未提交修改與空檔刪除，本輪不納入提交；不恢復人工刪除的文字。條文不宣稱法律登記或稅務資格，不設定新的修憲決策權。
