
# Council 治理制度

## 需求原文

/sf-ai 我會針對這個開一個 plan。那個 plan 裡面，至少要把 problem 落地到 specs 裡面，而且 problem 必須定義得非常清楚。

包含所有可能的弊端都要先定義清楚，像是權限、交接、腐敗等具體例子，都要盤得非常清楚，這樣你的 solution 才能避免掉那些弊端。

因為有清楚的 problem space，才會決定你的 solution 是不是精準。一個 problem 不夠清楚的政治基礎建設，不會有人理解你為什麼這樣設計，那個「Why did you do this kind of design?」的部分就不見了。

本 Plan 先定義 Problem，再比較 Solution；本輪不修改憲法、成員資格、Council 名單或平台。先前討論的席次、任期、重選、罷免與過渡安排均是候選，未採納。

## Problem 定義的核對

「Council 的產生、撤換與其他治理權未在該制度決定」直接對回自介審查的制度修改段；「Leader 選任、撤換、跨 R&R 爭議與制度核准尚未完整訂定」直接對回成員參與制度的接續、交接與完成段。兩者支持本輪需要補清治理依據，不支持推定既有成員曾濫權。

每組 Problem 均指出受影響的人、情境、想完成的事、失效因果及互相牽制的條件。以「審查者快速處理支持者」為例，這是假設，不是觀察；只有未來成員能參與任免時，才進一步產生操控任免參與者的後果。以「撤下 Council 身分時一併移除其一般成員與仍有效的 R&R 權限」為例，問題是多種有效身分被混同，不預設哪種撤任程序。

現有制度已有本人接受、交接及審查紀錄，故草稿不把問題寫成完全沒有規則；仍待處理的是規則之間的權限關係及例外。資金、正式成員規模與法律義務仍未知，保留為條件與後續查證事項，不能據此宣稱 Solution 已可落地。
